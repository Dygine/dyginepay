## The one thing that must not be confused

There are two money flows and they never touch.

| Flow | Payer | Receiver | Gateway |
|---|---|---|---|
| **Rent** | resident | PG owner | **the PG owner's own Razorpay keys** |
| **Subscription, wallet** | PG owner | **Krishna** | Dygine Pay's Razorpay account |

`billing.py`, `payment_gateway_service.py`, `/invoices`, `/payments` are all the
first flow and were not touched. `platform_billing.py`,
`platform_billing_service.py`, `/billing/platform/*` are the second.

Routing other people's money through one merchant account is payment
aggregation and needs an RBI licence. If a request would blur these two, say no.

## Where things live

**Wallet balance lives in Dygine.** PGuru caches it in
`org_billing_profiles.cached_wallet_paise` with a timestamp, for display only.
Every actual debit calls Dygine, which takes a row lock and decides. The UI says
"last known" when the cache is stale. Never authorise a spend from the cache.

**Coupons live in PGuru.** Dygine has never heard the word. PGuru computes the
discount and asks Dygine to collect the net, sending the discount as its own
invoice line so GST is charged on what the customer actually pays.

## Bugs found and fixed (all mine, all worth knowing)

These took most of the session. Each one failed **silently**, which is why they
were slow to find.

1. **Secret in the URL.** Issuing an API key redirected to
   `?secret=…`. Browser history, Render logs, referrer headers. Now a one-shot
   signed cookie.
2. **Three gates for one settings field.** A field must be declared in the
   frontend `WRITABLE` map, the `PlatformSettingsUpdate` schema, *and* the
   service's `WRITABLE` set. Any one missing and the value is discarded with a
   200 response. Cost two rounds. `test_platform_settings.py` now asserts the
   last two agree.
3. **An invented permission.** Guarded on `org.settings.manage`, which does not
   exist — the catalogue has `settings.manage`. Nav item vanished, route
   blocked, API 403'd everyone, notifications went nowhere. Four layers, no
   error. `test_permission_catalog.py` now parses every `require()`.
4. **No response envelope.** Every endpoint in PGuru returns `ok(payload)`;
   mine returned bare dicts. `unwrap()` reads `.data`, found nothing, handed the
   page `null`. The screen rendered from its fallbacks and looked merely empty.
   `test_response_envelope.py` now checks every route.
5. **Em dash in the invoice PDF.** fpdf2 core fonts are latin-1; the
   description PGuru sends contains `—`. 500 on every invoice. Now sanitised.
6. **Component API assumed, not read.** `Card` takes no `title`, `DataTable`
   columns use `header` not `label`, `StatCard` uses `sub` not `hint`,
   `EmptyState` uses `message` not `description`, `InlineAlert` uses `tone` not
   `variant`, `Skeleton` takes `className` not `rows`. This is what produced
   the broken layout.

**If you write anything here: read the component or the schema first. Do not
assume its shape.**

## Design decisions worth not undoing

**Money is integer paise in this subsystem.** The rest of PGuru uses
`Numeric(12,2)` rupees, which is right where a human types a figure and wrong at
a gateway boundary. `SubscriptionPlan.price` is Integer **rupees** — every
crossing goes through `rupees_to_paise()`, never a bare `* 100`.

**Capture is idempotent by construction.** The browser callback and the webhook
both call `checkout_service.complete()`; whichever is second finds it captured
and returns. This is why a customer whose phone dies still gets their
subscription.

**Coupon redemptions reserve → confirm → release**, counted under
`SELECT … FOR UPDATE`. Marking used at checkout burns the coupon on a failed
payment; marking it at success lets two people take the last one.

**Wallet debits take a row lock**, with a CHECK constraint as backstop. There is
a threaded test: ten concurrent ₹20 debits on ₹100 leave exactly five.

**Invoice numbers are taken under a row lock**, not `count(*) + 1`. Threaded
test: twelve concurrent invoices number 1–12 with no gaps.

**The wallet is a closed-loop PPI.** No cash out, no transfers between
customers, refunds only through the original payment. Break any of those and it
becomes a semi-closed PPI needing RBI authorisation.

**Invoice emails go out ~10 minutes after payment**, from the daily sweep, not
at capture. An SMTP conversation on the critical path of taking money turns a
slow mail server into a failed payment.

**The invoice seller is Dygine Software Solution and cannot be the product
name.** Krishna asked for this. An invoice names the supplier — the entity with
the PAN and the bank account. "PGuru" is a product, not a legal person. The PDF
shows the product as a `for PGuru` reference line instead, and the checkout page
shows the product name prominently with "Payments collected by Dygine Software
Solution" underneath, because the card statement carries the Razorpay account
holder and an unrecognised line is a chargeback.

## Still open

**GST.** `BUSINESS_GSTIN` is empty, so everything is a bill of supply with no
tax. Fill it and tax invoices start on the next payment, no code change.

**Wallet GST treatment.** Advances for *services* are taxable at receipt. The
code issues a tax invoice at top-up and treats consumption as a pure ledger
debit. **Needs a CA before he registers**, not before he ships.

**Both Render services are on the free plan.** They sleep after 15 minutes and
take ~50s to wake. This already caused a 502 on a Test connection. A webhook
arriving at a sleeping service times out — Razorpay and Dygine both retry, so
nothing is lost, but payments sit unconfirmed. **Starter ($7/mo each) before
real customers.**

**Still in Razorpay test mode.** See the production checklist beside this file.

## How to run either locally

```bash
# both
pip install -r requirements.txt
alembic upgrade head
uvicorn app.main:app --reload       # dygine-pay
# PGuru backend is the same; frontend is `npm install && npm run dev`
```

Tests need a real Postgres — the concurrency tests use threads against real row
locks, and a mock would prove nothing.

```bash
TEST_DATABASE_URL=postgresql+psycopg://… pytest -q
```

Dygine: 81 passing. PGuru billing + settings + envelope + permissions: 114
passing. PGuru's pre-existing suite has **6 failures that predate this work** —
refresh-cookie tests that fail on this Starlette version. Verified identical on
the untouched zip. Do not chase them.
